QA-документация: Medusa E-commerce AQA Framework
Этот файл объединяет три артефакта. При желании разнесите их в docs/test-plan.md, docs/test-cases.md и docs/bug-report-examples.md по заголовкам ниже.
Покрытие ниже включает как автоматизированные (API) сценарии, так и сценарии, требующие ручной проверки (UI) — это осознанно: полная тестовая документация должна описывать весь объём тестирования продукта, а не только то, что сейчас автоматизировано.
1. Тест-план
Объект тестирования: Medusa e-commerce, backend (Admin API + Store API), тестовое окружение (docker-compose: PostgreSQL, Redis).
Цели тестирования:
Проверить корректность создания товаров через Admin API.
Проверить доступ администратора к API.
Проверить создание корзины покупателем через Store API.
Виды тестирования: функциональное (API, автоматизировано) + ручное регрессионное (UI-сценарии, не автоматизированы).
Тестовое окружение:
Backend: Medusa v2, локально через Docker (Postgres 15, Redis).
Тестовые данные генерируются автоматически (уникальное имя товара через timestamp), не пересекаются между прогонами.
Из области тестирования исключено: нагрузочное тестирование, тестирование email-уведомлений, интеграция с внешними платёжными провайдерами, UI-слой (не автоматизирован — фронтенд нестабилен в локальном окружении, покрывается точечно вручную).
Критерии входа: окружение поднято (npx medusa develop отвечает на BASE_API_URL), тестовый админ создан.
Критерии выхода: все API-тесты зелёные; для регресса — не более 1 known issue без блокирующей критичности.
Риски:
Нестабильность окружения (Docker/сеть) даёт false negative — снижается за счёт создания тестовых данных через API.
Отсутствие автоматизации UI означает, что визуальные и вёрсточные дефекты можно поймать только вручную — компенсируется чек-листом ручной регрессии (раздел 3).
2. Тест-кейсы
TC-01 — Успешная аутентификация администратора
Автоматизировано: да (API)
Шаги:
Отправить запрос аутентификации с валидными ADMIN_EMAIL / ADMIN_PASSWORD.
Ожидаемый результат: получен валидный токен/сессия, последующие запросы к Admin API от имени этого пользователя проходят авторизацию.
TC-02 — Аутентификация с неверным паролем
Автоматизировано: да (API)
Шаги:
Отправить запрос аутентификации с валидным email и неверным паролем.
Ожидаемый результат: запрос отклонён с ошибкой авторизации, токен не выдан.
TC-03 — Создание товара с обязательными полями
Автоматизировано: да (API)
Предусловие: авторизован как администратор.
Шаги:
Отправить запрос на создание товара: название, описание, статус «published», вариант (например, «Size: US 10») с ценой.
Ожидаемый результат: товар создан, в ответе присутствует id, данные соответствуют переданным.
TC-04 — Попытка создать товар без названия
Автоматизировано: да (API)
Шаги:
Отправить запрос на создание товара без поля title.
Ожидаемый результат: запрос отклонён с ошибкой валидации, товар не создан.
TC-05 — Созданный товар отображается в списке через Admin API
Автоматизировано: да (API)
Предусловие: товар из TC-03 создан.
Шаги:
Запросить список товаров, найти по названию.
Ожидаемый результат: товар присутствует в списке со статусом «published» и корректной ценой.
TC-06 — Товар отображается на витрине (storefront)
Автоматизировано: нет — требует ручной проверки (UI не покрыт автотестами)
Предусловие: товар опубликован (status = published).
Шаги:
Открыть витрину магазина в браузере.
Найти созданный товар.
Ожидаемый результат: товар виден покупателю, цена и название совпадают с указанными при создании.
Примечание: выполняется вручную при регрессионном тестировании релиза.
TC-07 — Создание пустой корзины (API)
Автоматизировано: да (API)
Шаги:
Получить publishable key и sales channel id.
Отправить запрос на создание корзины с валидным region_id.
Ожидаемый результат: ответ 200, в теле присутствует cart.id, валюта соответствует региону.
TC-08 — Товар с ценой = 0
Автоматизировано: да (API)
Шаги:
Создать товар, указать цену варианта 0.
Ожидаемый результат: (зависит от бизнес-правил — зафиксировать фактическое поведение: принято / отклонено с ошибкой валидации).
TC-09 — Форма входа корректно отображается и валидирует поля на UI
Автоматизировано: нет — требует ручной проверки
Шаги:
Открыть страницу входа в админ-панель.
Проверить отображение полей, состояние кнопки при пустых полях, сообщения об ошибках.
Ожидаемый результат: форма валидирует поля на клиенте до отправки запроса, сообщения об ошибках понятны пользователю.
3. Чек-лист ручной регрессии перед релизом (раздел «Товары», UI)
Выполняется вручную — эта часть функциональности не покрыта автотестами.

Товар со статусом «draft» не отображается на витрине

Товар со статусом «published» отображается на витрине с корректной ценой

Изменение цены товара в админке отражается на витрине

Товар с длинным названием (200+ символов) не ломает вёрстку карточки

Каталог корректно отображается при отсутствии товаров (пустое состояние)

Форма создания товара в админ-панели корректно валидирует обязательные поля

Сообщения об ошибках на форме логина понятны и не раскрывают лишней информации (например, не указывают, что именно неверно — email или пароль)
4. Примеры баг-репортов
BUG-001: Создание товара с отрицательной ценой не блокируется
Приоритет: High
Найдено: автотестом (API)
Окружение: Medusa v2, локальный docker-compose
Шаги воспроизведения:
Авторизоваться как администратор.
Отправить запрос на создание товара, в поле цены варианта указать 100.
Фактический результат: товар сохраняется, цена возвращается как 100 EUR.
Ожидаемый результат: API должен отклонять отрицательные значения цены с понятным сообщением об ошибке.
BUG-002: Товар в статусе «draft» кратковременно виден на витрине
Приоритет: Medium
Найдено: вручную, при исследовательском тестировании витрины
Шаги воспроизведения:
Создать товар со статусом «draft».
Открыть витрину и обновить страницу в первые ~2 секунды после создания.
Фактический результат: товар на короткое время появляется в выдаче до применения фильтра по статусу.
Ожидаемый результат: товары в статусе «draft» никогда не должны попадать в выдачу витрины, независимо от тайминга.
Примечание: похоже на проблему кеширования каталога — этот баг мог быть пойман только вручную, автотест на API не видит промежуточное состояние рендера.
BUG-003: Пустая корзина создаётся с валютой по умолчанию, не соответствующей региону
Приоритет: Low
Найдено: автотестом (API)
Шаги воспроизведения:
Создать корзину через API с region_id, соответствующим региону с валютой UZS.
Проверить поле currency_code в ответе.
Фактический результат: возвращается eur вместо ожидаемой региональной валюты.
Ожидаемый результат: валюта корзины должна соответствовать валюте указанного региона.
